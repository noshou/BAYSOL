BAYSOL terminal interface

The terminal interface (TUI) is a full-screen program for using BAYSOL without writing code: you make a project, put its 3D model, its measured curve and its buffer into it, press one key to fit, and read the results in the same window. It is written in TypeScript with Ink (React for the terminal) and runs in any terminal of at least 80 columns by 24 rows; nothing has a fixed width, lists scroll and text wraps. It looks best with 24-bit colour. The fit itself is the Julia package: the interface starts Julia as a child process, shows its output live, and reads the files it writes.

This page is the user guide and the reference; the internals page is for contributors. The same steps, shorter, are in the first guide of the repository's main README.

Install and start

The packaged app (a bundle with its own Julia, Node and a precompiled BAYSOL, made by bysl pkg) starts with its launcher, baysol. The launcher sets BAYSOL_BUNDLE (the folder of the app) and, from install.json in the per-user config folder, BAYSOL_HOME, BAYSOL_CACHE and BAYSOL_THREADS (a variable you set yourself wins). On the first start (no install.json, a terminal) it opens the setup wizard; later baysol setup opens it, and so does shift+a on the main menu. The wizard sets the projects folder, the caches, the threads per fit and the shortcuts (desktop entry, PATH link), repairs the shortcuts and uninstalls (the app and caches, or everything including the projects, which asks for the word delete). Nothing is written until you apply; changes apply at the next start. After an uninstall the terminal interface quits (the wizard's exit status 22). The help page says the same.

The rest of this section is the source checkout.

You need Julia 1.12, Node.js 24 or newer (node --version) and a BAYSOL folder that contains tui/. The repository has one node_modules, at its root: tui is an npm workspace of the root package.json.

cd BAYSOL                  # the repository root
npm install                # once, here, not in tui/
julia --project=. -e 'using Pkg; Pkg.instantiate(); using BAYSOL'   # once: the fitting code
cd tui
npm start                  # every time (runs `tsx src/main.tsx`)

The julia line downloads and compiles BAYSOL (several minutes) so that the first fit is not the one that waits; a first fit also downloads the helper programs PROPKA and pdb2pqr and needs internet. A run starts julia --startup-file=no --color=no --threads=auto,1 --project=<repository root> ...; the program is julia on the PATH, or the one named by the environment variable JULIA.

Started with no terminal (a launcher) the program opens a terminal emulator that runs it again (Linux: $TERMINAL, the desktop's terminal, then every known one; macOS untested; on Windows Windows Terminal, else a new console window); the copy that was opened never opens a second one, and a pipe prints BAYSOL: this program needs a terminal and stops. npm start -- --view FILE opens a workbook or table in the viewer instead of the main menu. Made smaller than 80 x 24 it shows a message in place of the screen and returns to the same screen when the terminal is big enough again. The release name on the main menu comes from the repository's Project.toml.

The data folder holds everything you make. It is chosen like this:

The interface has been run on Linux and on Windows 11. The macOS parts (the desktop file chooser, also of the references, opening a folder in the file manager) are written from the system's documentation and are untested. The rest behaves the same everywhere. The one place that reads the operating system is src/core/environment.ts (see the internals).

A first session in ten steps

  1. npm start. On the main menu press n, type demo, press Enter: the project menu opens.
  2. m (models): paste the full path of a .cif or .pdb, press Enter. ^x goes back.
  3. d (data), load a file: paste the path of your curve, Enter; check the three columns in the preview; press ^w.
  4. On the data screen, set q units (Enter or ^k toggles) and energy (nm by default; ^k turns the unit label).
  5. ^x, then b (buffer), Enter on buffer: ^g for the pH and the temperature (7.4 0.1, then 25), ^n for each solute (name, concentration, ±; ^k turns the unit), ^w to save.
  6. ^x to the project menu. A run: shift+r item appears at the bottom once everything is there.
  7. Press shift+r: the run starts at once, at the buffer's temperature.
  8. Watch the run screen. When it says done, press Enter.
  9. o (open...), open runs, Enter on the model: the results workbook. shift+p shows the plots.
  10. ^l on a run reads its log; ^x goes back; ^x again and q on the main menu quits.

Screens and keys

Moving around

Move with the arrow keys and press Enter, or press the hotkey of an option. The hint at the bottom lists the keys that work from where the cursor is, and nothing else; the footer's height depends on the screen only, so the logo at its left never jumps. The table-style screens (the buffer table, the custom solutes table and forms, the settings sheets, the logs pages) are blocky: the blocky logo, double-line tables, the footer in a double-line box. Every other screen is smooth: the rounded logo, rounded panels, thin single-line tables, the keys of the footer each in a small rounded box (in columns, as on the blocky screens, when the boxes do not fit one row).

  • Esc closes what is open (a prompt, a list, a question, a pager). It never quits and does nothing at menu level.
  • ^x goes back one screen, from any mode. It never quits.
  • q on the main menu, ^c and ^d are the only ways to leave the program. ^c and ^d first stop a run that is going, then leave.
  • ^t opens the theme list on any screen (also during a run).
  • ^s, ^q, ^z and ^y are taken by the terminal; ^m, ^i, ^j arrive as Enter, Tab and Enter.
  • Unsaved changes ask (discard N changes?: Enter discards, Esc keeps) when you leave a screen with unsaved changes. Removing anything you made asks (delete X? this cannot be undone!: Enter deletes, Esc keeps).

The theme list (^t)

All 20 themes at once, alphabetical, each with an emoji, four colour swatches and its mode: abyssal, arboreal, autumn, citron, graphite, holograph, invert, lavender, luxe, mate, onigiri, pamplemousse, parchment, rose, syrah, terracotta, tweedia, ultrapink, ursus, vt100 (ten light, ten dark). Arrows move, Enter picks, Esc or ^t leaves. The pick is saved by name in theme.json and is the theme of the next start; the bottom right of every screen reads theme (^t): <name> <emoji>. The program only paints cells; it never changes your terminal's own colours.

Models

models takes the full absolute path of a .cif or .pdb file. Names are hinted as you type and Tab completes. The file is copied into the project's models.7z archive (copied lyz.cif; 7-Zip, one solid LZMA2 block, rewritten atomically); the original is never touched, and an existing name is never overwritten. A project can hold several models; a run fits each in turn. The archive is written in the background: the note says adding <name>... (a list row says (removing...)) while 7-Zip works, the screen stays usable, and the list is read again when the write ends. Leaving the screen or quitting (^c, ^d) first lets the write finish, and the archive is replaced only as a whole, so it is never left half written.

KeyDoes
^v (on an empty field)pick files in the desktop file chooser
shift+h (on an empty field)list the project's models (models (N): shift+h)
^r or Delete (on the list)delete the highlighted model after a question
^o (on the list)the settings of the highlighted model (below)

Settings of one model. On the list ^o opens the settings of the highlighted model: the same sheets as the project's, but only the settings that can differ from model to model (output has only VAL_SIGMA and plots is not offered: the figures' look, TABLE_SIGFIGS and FIGURES_* are settings of the whole run, so a model cannot have them). The title says model: <name>. Every setting shows its value and, in the last column (headed here), overridden (the model's own, in the full colour) or inherited (the project's value, muted). Edit as on any sheet: a value that differs from the project's becomes an override, a value equal to it removes the override (so the file stays sparse), ^u undoes the change under the cursor and ^r (inherit group) gives the group the project's values again. ^w saves into model-settings.json of the project (only the changed settings of this model, under a lock, over the file as it is then; another copy's changes to other settings or models are kept). In the list a model with overrides has a * and the note under the list says overrides: Q_MAX, N_CHAINS. A model that is renamed or deleted leaves its table in the file (a run ignores it with a note); the program never removes it. An invalid value, or a setting of the whole run, found in the file is wiped when the model's sheet opens (one line in settings.log, model <name>: <SETTING>). An override stays when the project's own value changes later, even when it comes to equal it (only an edit to the project's value, or inherit group, removes it), unless the two then break a rule (a model's Q_MIN above the project's Q_MAX): that override is wiped.

The summary lines of the screen show reference fit, ref software, ref chi2 and ref rescale once there is one. reference software (MultiFoXS 2-state), reference chi2 (the depositor's, with its method: MultiFoXS 2-state 0.79) are text prompts and reference rescale toggles scaling the curve onto the data by least squares (for a normalized fit); each change is saved at once into the entry * of <project>/model-references.json. ^r on a reference row deletes the curve after the question and clears the entry. The screen shows the file named by the entry *, else the usable file changed most recently. A run copies the folder, model-settings.json and model-references.json into its run folder with the other inputs (the curves as reference-fit-<file>).

  • A wrong file or wrong columns is a warning, never a stop. The note line says so while the columns are chosen and again after the import: sigma is about I: a fit file? wrong file? (the sigma column of a measured curve is as big as I(q) and follows it: a SASBDB .fit file read as q, I, sigma, whose third column is the model); for a reference fit, same numbers as the data: the model column?, 5.2x off the data: wrong column? (the median distance from the measured curve on its q) or q range does not meet the data: units?.

  • The reference on the figure of a model. The project's reference fit (above) is drawn on every model's figure (<model>_comparison.tex): the data, the reference curve (software (chi2) in the legend) and the MAP curve with its own χ², and refChi2 is written in the model's LOG. The model screen has no reference rows.

A project can run only with valid data and an energy. A data file that cannot be used is told, never written over, and r puts it aside as .corrupt.

Buffer

buffer is a small page with up to five rows, buffer (N solutes), custom solutes (N), load a recipe, new recipe and, for a buffer that has solutes, save current recipe globally, and a one-line status of each file (buffer: none yet, pH not set, buffer: unusable!). shift+z on an unusable file offers to reset it.

Recipes are named buffers kept in the data folder (recipes.json, shared by every project). save current recipe globally asks a name (replace "NAME"? if one has it) and saves the buffer as it is on disk, with its pH and σ. load a recipe lists the saved recipes with their solute counts (type to find one: the list narrows as you type; ^r deletes the highlighted one, after a question) and opens the buffer table with the recipe's rows as unsaved ones (*); the recipe's pH, σ and temperature, when it has them, come in as an unsaved change of the pH row (a recipe without leaves the buffer's own; one without a temperature leaves the buffer's temperature). At the first ^w a buffer that has solutes asks replace N solutes with recipe "NAME"?. new recipe opens the table empty and replaces nothing before ^w. Nothing is written before ^w; the recipe is copied, not linked. The unit ^k is not part of a recipe. Global settings has two more options under the four groups: recipes (y) and solutes (t) open the recipes table and the custom solutes table; shift+z on an option whose file cannot be used offers to reset it (the old file stays as <name>.corrupt). In the recipes table, the custom solutes table and the buffer table, / finds a row by name (type part of it, ⏎ puts the cursor on it) and shift+s puts the rows in alphabetical order (shown only while they are not); the recipes and the custom solutes also open in that order. The shift+z reset legend shows only on the row whose file cannot be used. The path prompts (data, reference fit, models) are boxed like the other dropdowns. Template recipes. A recipe can be a template: it keeps its definition inside the recipe ("template" in recipes.json), so that what depends on the pH and the temperature is worked out when it is loaded. Three kinds: builtin (a shipped buffer: concentration, ±, titrant, pH set at, rest of the recipe), custom (your own buffer: 1 to 3 pKa steps with the pKa at 25 °C, d(pKa)/dT and the charge of the acid form, a titrant acid or base with its ion, concentration and ±; run by the same engine, labelled constants not sourced) and table (amounts of each row at two or more pH, interpolated linearly, a pH outside the points refused). The recipe's solutes are its fixed rows (salt, protein, ...). Make one with shift+w on the recipes table (a name, then the questions) or on the buffer table (the rows come in linked and follow the pH and temperature), or save a buffer whose rows follow one template with save current recipe globally (it asks save "NAME" as a template?; Enter saves the template, shift+x a plain recipe, Esc saves nothing; rows of two templates cannot be one). The recipes table has a template column while one exists. Loading a template recipe adds its fixed rows and the rows of its definition at the recipe's pH and temperature (else the buffer's; no pH at all asks you to set it first), and they follow the buffer table's pH and temperature (a table outside its points leaves the rows as they are and says so). A definition that does not check makes the recipe invalid: its fixed rows load and the problem is the hint (editing the template fixes it). shift+e on the recipes table edits the definition of the recipe under the cursor: the wizard starts from it, every question prefilled, Esc leaves it unchanged. shift+v on the buffer table turns its rows (bundled and custom non-biological solutes that do not follow a template yet) into a table template: they are the first point, at the table's pH, the wizard asks the other pH and the amounts there, and the rows come back linked in place of the typed ones (save the buffer as a template to keep it). The wizard takes your custom solutes wherever it takes a solute (a custom buffer's solute, the rows of a table); the definition then holds a snapshot of the solute (z, pmv, sigmaPmv), so it needs no custom file. Julia never sees a definition (it reads rows only; a row's template key is ignored). Buffer templates. shift+b fills the rows of a standard buffer the way the fitting scripts do by hand: the buffer's own row at the concentration you typed, plus the counter-ion that setting the pH adds (chloride for Tris and the other amine bases titrated with HCl; sodium or potassium for the others, with NaOH or KOH; polyprotic buffers such as phosphate and citrate as their salts). The pK of each step is moved to the temperature the pH was set at (the pH set at question: the buffer's temperature by default, 22 °C as the scripts assume, or a number; the confirm page says which), the species at the pH come from Davies activity coefficients (A = 0.509) at the ionic strength of the whole recipe, solved self-consistently, and the ± combines the pH meter's σ, ±3 °C, ±0.02 in pK, 30 % of the Davies shift and the uncertainty of the concentration. Davies is unreliable above 0.5 M and a pH outside the usable range of the buffer is allowed but warned about; the pH is kept within 0 to 14. Constants and sources: notes/buffer-templates.md; a template whose constants were not cross-checked is labelled (constants not cross-checked). Mixtures (PBS, TBS, HBS, SSC) give their rows as listed and the pH to set. The rows are ordinary rows (new, shown with *, editable, saved by ^w); the pH row is set when empty or when the page says it changes it. An older link without setAt means 22 °C. Structure files. A .pdb/.ent file gives its SEQRES chains, a .cif/.mmcif file its _entity_poly entities; only the chains of the asked kind are taken, chains with the same sequence become one row (1abc_A+B), a modified residue is its parent (a short built-in table; X or N when unknown), and a PDB with no SEQRES (most model files) gives its chains from the ATOM records of the first MODEL (waters, ions and ligands such as heme are no sequence; a residue missing from the model is missing from the sequence), and a file with none of the kind is refused with a hint (no DNA in the file (it has protein: use ^f)).

Sequences as text. The path: prompt of ^f and ^e takes a file path or the sequence itself. Text with a /, \, ., ~ or : is a path (an existing file is read; otherwise no such file or use a full path); anything else is linted as a sequence. A paste of several lines (a whole FASTA) or longer than the field is taken at once and counted (pasted 12 residues: enter takes them); Enter takes it, typing forgets it. One lint serves text and files: a > header line, spaces, line breaks and the numbers of a GenBank-style listing are dropped and letters are upper-cased; nothing else is repaired. A wrong character is an error that names it and its place (invalid residue '-' at 12, U is RNA, not DNA (at 4), T is DNA, not RNA (at 4), empty sequence); the letters allowed are the ones Julia accepts (DNA/RNA: ACGT or ACGU plus the IUPAC codes; protein: every letter, X and * count as no residue). Text with no header is one row, seq1.

Rows made from one file share its mM and ±; edit them afterwards. The params column shows n/a for a small molecule and the sequence (with its length) for a protein or nucleic acid. These rows are what is in the buffer blank: never list the molecule you measured.

The pH and its σ. Both are saved together in buffer.json (pH and sigmaPh, each from 0 to 14); a pH without a σ, or out of range, makes the file unusable. A buffer with no pH is not ready to run. The unit ^k turns (mM, M, µM) is kept in the same file as conc-unit (written at once, and with every save); a missing or unknown value opens in mM, and Julia ignores the key.

Run

The project must have a model, a buffer with at least one solute, a pH and a temperature, and data with its energy. Then the project menu shows run: shift+r. shift+r starts the run at once, with the temperature kept in the buffer (buffer.json, set with ^g after the pH and σ; 0 to 100 °C, no uncertainty). If the program or the machine dies, Julia ends its run when its input closes, and a running run whose heartbeat is over a minute old is marked interrupted by whichever copy of the program notices it.

The command line of a run

Every setting that runProject takes as a keyword is a flag, so a run needs no terminal interface:

julia --project=tui/julia -e 'using BAYSOLRun; exit(BAYSOLRun.runProjectCli(ARGS))' -- \
    PROJECT --temperature 20 --nDraws 800 --memory-headroom 25 \
    --ladder 'divergent=[{"name": "wide", "overrides": {"TARGET_ACCEPT": 99}}]' \
    --model-setting 'm1={"qMin": 0.03}'

--<name> VALUE is the setting by the name of its keyword (--nDraws, --n-draws and --N_DRAWS are alike); VALUE is JSON (800, false, null, [1, 2, 3]) or plain text. --ladder takes off, a JSON map from failure class to rungs, the path of a JSON file, or one class as CLASS=JSON (repeatable: the classes add up); --model-setting MODEL=JSON gives settings to one model (repeatable; a JSON object from keyword to value, or a file). --temperature is required, --run-dir and --n-samples are optional, --help prints the list. A value is judged exactly as the same value in settings.json is, and a wrong one is refused before anything starts (exit status 2). Precedence is command line, then the settings files, then the defaults. The plot-look settings (PLOT_* other than the comparison switches) are set in settings.json; they are no flags.

The run archive

When Julia has finished (a run that is done, failed or aborted) the program packs the run folder: the screen says packing, then done. EVERYTHING of <run>/ goes into ONE 7z archive beside the folder, runs/<run>.7z, and the folder is removed: run.json, the workbooks, the logs, the inputs and the plots, as FLAT names (run.json, run.LOG, plots.txt, settings.json, ..., <model>.LOG, <model>.xlsx, <model>.tex, <model>-plots.txt, <model>-76x10.txt, compare.tsv, compare.tex, compare-plots.txt, ...), at the best compression (-mx=9). The run's name is the same with or without the archive, a run that is still going (or whose pack failed) is the plain folder runs/<run>/, and the readers take either; run.json of an archive is read once and kept while the archive stays as it is, so the run list stays fast. A workbook goes into the archive as the tree of its unzipped XML files (m.xlsx as m/[Content_Types].xml, m/_rels/.rels, m/xl/...), which 7-Zip compresses much better than the zip it already is; the archive is packed with the highest settings (x=9, word size 273, solid, all from run_flow.json). A workbook that is only in the archive is zipped again from its tree into a proper .xlsx ([Content_Types].xml first, deflated, the same bytes every time; at level 0 the zip is stored without compression by the program's own writer, src/core/zip-writer.ts, since 7-Zip sorts the entries by name, with zip64 structures where a size or a count needs them) in a copy in the program's temporary folder (see Temporary files below); files moved to the data folder are always proper .xlsx files.

The screen is painted again in place every screen.refreshSeconds idle seconds (run_flow.json, default 5, 0 = off), on a resize and when the terminal gains focus, never over a sixel picture (a workaround for stray characters; notes/tui.md, "Screen refresh (workaround)").

The pack is atomic: the archive is made as <run>.7z.tmp.<pid>, tested with 7z t and compared with the list of what was packed, and only then renamed to <run>.7z; the packed originals are removed after that and never before. If anything fails (a full disk, a failed test) the run folder stays exactly as it was, the staged file is removed, and the note row on the run screen says why (not packed: ...); the run's own outcome is unchanged. While a pack runs, deleting that run is refused with this run is being packed.

Reading is the same for packed and plain runs. The viewer's plots (shift+p), run.LOG (^l and view run.LOG), the logs menu (every view, conditions, the restores) read the archive or, for a run that was never packed, the plain folder; the plots are read straight out of the archive (nothing is extracted to disk), always read-only, with a check of every entry name (no .., no absolute path) and a size cap per entry. Extracting (move and compile plots) uses a temporary folder of the program (removed right after use). The archive is made by 7-Zip (the 7zip-bin binary, run through node-7z; a 7z, 7zz or 7za on the PATH is the fallback when the bundled one cannot run).

Temporary files. Every temporary file the interface makes lives under ONE root, baysol in the temporary folder of the system (<tmp>/baysol, Platform.tmp_dir in platform.jl, tmpFolder in src/core/environment.ts), with one folder per process, <tmp>/baysol/<pid>/, and a folder per purpose in it (view: the .xlsx copies the viewers open, capped in size; run-models and run-cache: what a running fit reads and writes; book, pack, add, run, sixel, extract, move, compile: the staging folders of one operation, removed as soon as it is done; native: the natives when the cache's copy is locked). No other code asks for the system's temporary folder (a test checks src). src/core/scratch.ts keeps it clean: at start (before the first screen) it removes the folders of processes that are no longer running (a crash, a closed terminal, a power loss; a pid is dead when process.kill(pid, 0) says ESRCH, so a folder whose pid another program reuses waits until that program ends) and, once, the folders older versions left loose in the temporary folder (baysol-<pid> of a dead pid; baysol-book-*, baysol-pack-*, baysol-run-*, baysol-add-*, baysol-sixel-*, baysol-extract-*, baysol-move-*, baysol-compile-* older than a day; nothing else); every 30 minutes (a timer that does not keep the program alive) it removes what nobody touched for an hour and evicts the least recently used entries while the process folder is over 2 GiB (never the models of a running fit, its cache or the natives); and an exit hook, registered at start, removes the process folder on every way out: ^c, ^d and Quit from the main menu end the program normally, SIGHUP and SIGTERM call process.exit, an uncaught exception still emits exit. On Windows a signal sent with kill ends the program without running anything, and a closed console arrives as SIGHUP; a killed program (or a power loss) leaves its folder for the next start to remove. The system wipes its temporary folder now and then too. The cache folder (BAYSOL_CACHE) is different: it holds only what must last (the structures later runs reuse, fonts.json, and the natives of the single executable in native/, ONE folder holding one version's files and a .version stamp, replaced when the version changes), and the interface never clears it; only the setup wizard does (Clear cache, Uninstall).

The terminal interface manages projects for you; a script uses plain folders. The interface keeps the models and the reference curve of a project in models.7z and reference-fit.7z, and for each run it unpacks what Julia reads into the program's temporary folder, hands Julia a private cache folder holding the generated files stored in models.7z (BAYSOL_CACHE; the downloaded component files stay in the shared cache) and, when the run is over, stores the files Julia generated back into models.7z. Deleting a model deletes the files generated from it. Julia itself takes plain files and folders and never reads an archive: to run a project from a script (runProject), put the models in <project>/models/ (.cif and .pdb files) and the curves in <project>/reference-fit/. For a project that was made in the interface, extract them first, in the project folder:

7z x models.7z -omodels            # the generated/ folder inside is ignored
7z x reference-fit.7z -oreference-fit

Two copies at once

Two copies of the program, or the program and a Julia script, can use the same data folder safely. Saving takes a short lock on the file. Settings changed in two copies are merged (the same setting: the last save wins). A buffer or custom-solute list that another copy saved meanwhile is not overwritten (changed on disk: reopen it). A project deleted in one copy is not brought back by the other. Starting a run takes a lock too, so two copies starting at the same instant cannot both win; a refused start says a run is in progress (pid N), and delete run and delete project refuse a live run.
