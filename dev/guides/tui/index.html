BAYSOL terminal interface

The terminal interface (TUI) is a full-screen program for using BAYSOL without writing code: you make a project, put its 3D model, its measured curve and its buffer into it, press one key to fit, and read the results in the same window. It is written in TypeScript with Ink (React for the terminal) and runs in any terminal of at least 80 columns by 24 rows; nothing has a fixed width, lists scroll and text wraps. It looks best with 24-bit colour. The fit itself is the Julia package: the interface starts Julia as a child process, shows its output live, and reads the files it writes.

This page is the user guide and the reference; the last section is for contributors. The same steps, shorter, are in the first guide of the repository's main README.

Install and start

You need Julia 1.12, Node.js 22 or newer (node --version) and a BAYSOL folder that contains tui/. The repository has one node_modules, at its root: tui is an npm workspace of the root package.json.

cd BAYSOL                  # the repository root
npm install                # once, here, not in tui/
julia --project=. -e 'using Pkg; Pkg.instantiate(); using BAYSOL'   # once: the fitting code
cd tui
npm start                  # every time (runs `tsx src/main.tsx`)

The julia line downloads and compiles BAYSOL (several minutes) so that the first fit is not the one that waits; a first fit also downloads the helper programs PROPKA and pdb2pqr and needs internet. A run starts julia --startup-file=no --color=no --threads=auto,1 --project=<repository root> ...; the program is julia on the PATH, or the one named by the environment variable JULIA.

Started with no terminal (a launcher) the program opens a terminal emulator that runs it again (Linux: $TERMINAL, the desktop's terminal, then every known one; macOS and Windows untested); the copy that was opened never opens a second one, and a pipe prints BAYSOL: this program needs a terminal and stops. npm start -- --view FILE opens a workbook or table in the viewer instead of the main menu. Made smaller than 80 x 24 it shows a message in place of the screen and returns to the same screen when the terminal is big enough again. The release name on the main menu comes from the repository's Project.toml.

The data folder holds everything you make. It is chosen like this:

The macOS and Windows parts (the desktop file chooser, also of the references, opening a folder in the file manager, stopping a run on Windows) are written from the systems' documentation and are untested. The rest behaves the same everywhere.

A first session in ten steps

  1. npm start. On the main menu press n, type demo, press Enter: the project menu opens.
  2. m (models): paste the full path of a .cif or .pdb, press Enter. ^x goes back.
  3. d (data), load a file: paste the path of your curve, Enter; check the three columns in the preview; press ^w.
  4. On the data screen, set q units (Enter or ^k toggles) and energy (nm by default; ^k turns the unit label).
  5. ^x, then b (buffer), Enter on buffer: ^g for the pH and the temperature (7.4 0.1, then 25), ^n for each solute (name, concentration, ±; ^k turns the unit), ^w to save.
  6. ^x to the project menu. A run: shift+r item appears at the bottom once everything is there.
  7. Press Shift+R: the run starts at once, at the buffer's temperature.
  8. Watch the run screen. When it says done, press Enter.
  9. o (open...), open runs, Enter on the model: the results workbook. ^p shows the plots.
  10. ^l on a run reads its log; ^x goes back; ^x again and q on the main menu quits.

Screens and keys

Moving around

Move with the arrow keys and press Enter, or press the hotkey of an option. The hint at the bottom lists the keys that work from where the cursor is, and nothing else; the footer's height depends on the screen only, so the logo at its left never jumps. The table-style screens (the buffer table, the custom solutes table and forms, the settings sheets, the logs pages) are blocky: the blocky logo, double-line tables, the footer in a double-line box. Every other screen is smooth: the rounded logo, rounded panels, thin single-line tables, the keys of the footer each in a small rounded box (in columns, as on the blocky screens, when the boxes do not fit one row).

  • Esc closes what is open (a prompt, a list, a question, a pager). It never quits and does nothing at menu level.
  • Ctrl-X goes back one screen, from any mode. It never quits.
  • q on the main menu, Ctrl-C and Ctrl-D are the only ways to leave the program. Ctrl-C and Ctrl-D first stop a run that is going, then leave.
  • Ctrl-T opens the theme list on any screen (also during a run).
  • ^s, ^q, ^z and ^y are taken by the terminal; ^m, ^i, ^j arrive as Enter, Tab and Enter.
  • Unsaved changes ask (discard N changes?: Enter discards, Esc keeps) when you leave a screen with unsaved changes. Removing anything you made asks (delete X? this cannot be undone!: Enter deletes, Esc keeps).

The theme list (^t)

All 20 themes at once, alphabetical, each with an emoji, four colour swatches and its mode: abyssal, arboreal, autumn, citron, graphite, holograph, invert, lavender, luxe, mate, onigiri, pamplemousse, parchment, rose, syrah, terracotta, tweedia, ultrapink, ursus, vt100 (ten light, ten dark). Arrows move, Enter picks, Esc or ^t leaves. The pick is saved by name in theme.json and is the theme of the next start; the bottom right of every screen reads theme (^t): <name> <emoji>. The program only paints cells; it never changes your terminal's own colours.

Models

models takes the full absolute path of a .cif or .pdb file. Names are hinted as you type and Tab completes. The file is copied into the project's models/ folder (copied lyz.cif); the original is never touched, and an existing name is never overwritten. A project can hold several models; a run fits each in turn.

KeyDoes
o (on an empty field)pick files in the desktop file chooser
m (on an empty field)list the project's models (models (N): m)
^r or Delete (on the list)delete the highlighted model after a question
^o (on the list)the settings of the highlighted model (below)

Settings of one model. On the list ^o opens the settings of the highlighted model: the same sheets as the project's, but only the settings that can differ from model to model (output has only VAL_SIGMA and plots is not offered: the figures' look, TABLE_SIGFIGS and FIGURES_* are settings of the whole run, so a model cannot have them). The title says model: <name>. Every setting shows its value and, in the last column (headed here), overridden (the model's own, in the full colour) or inherited (the project's value, muted). Edit as on any sheet: a value that differs from the project's becomes an override, a value equal to it removes the override (so the file stays sparse), ^u undoes the change under the cursor and ^r (inherit group) gives the group the project's values again. ^w saves into model-settings.json of the project (only the changed settings of this model, under a lock, over the file as it is then; another copy's changes to other settings or models are kept). In the list a model with overrides has a * and the note under the list says overrides: Q_MAX, N_CHAINS. A model that is renamed or deleted leaves its table in the file (a run ignores it with a note); the program never removes it. An invalid value, or a setting of the whole run, found in the file is wiped when the model's sheet opens (one line in settings.log, model <name>: <SETTING>). An override stays when the project's own value changes later, even when it comes to equal it (only an edit to the project's value, or inherit group, removes it), unless the two then break a rule (a model's Q_MIN above the project's Q_MAX): that override is wiped.

  • q units: Enter or ^k turns the unit of q and saves it at once (^k is the unit key of q, energy and concentrations; on any other row it only says so) (Å⁻¹ or nm⁻¹) at once into data.json (the TSV is never rewritten). A new curve starts as Å⁻¹. Julia divides q by 10 when it reads nm⁻¹.

  • energy: the X-ray energy as typed, above 0, saved at once. There is no default value; a new entry is read in nm (a wavelength). Numbers only. ^k (in the prompt or on the menu) turns the unit label nm, Å, eV, keV like the q units: the number is never changed, only how it is read (saved as energy_unit in data.json); data.json always holds it; Julia converts to eV at run time.

  • change the columns reopens the import on the stored source with the stored choices. If the source file is gone it says source is gone: <name>; an old data.json without a mapping says no source recorded: load a file.

  • reference fit opens the list of the project's reference curves (the depositor's CRYSOL or FoXS fit, ...) that a run draws in its comparison figure. They are the files of <project>/reference-fit/). The summary of the data screen says reference fit 2 (name1, name2) when there are some. The list opens at any time, but adding needs data (import the data first), because a reference is in the same units as the data (units turns them for both). The list shows each curve's name, its points (those with q and I above 0, the ones a run draws) and its q range. ^n adds one: a path prompt as for load a file, then the same import screen (titled reference fit, the units in its subtitle) with roles q and I(q) and an optional sigma. The columns start as the depositors' fit files come: q is col:1, I(q) is col:3 (the model's intensity; a table of two columns takes col:2) and sigma is none (a chosen sigma is written, but a run reads and ignores it); the preview rounds numbers to five digits. ^w adds. Rows with q (or a chosen sigma) not above 0 are dropped as in the data import, at least 3 points are needed. The file written is clean: <name>.tsv, two or three tab-separated columns, no header. The name is the source's file name without its extension, with every character that is not a letter, digit, -, _ or . made _; a taken name gets -2, -3, ..., so nothing is ever overwritten. ^r (or Delete) deletes the highlighted one after the question. A file in the folder that a run could not read is listed as unusable (its reason, such as line 3: a cell is no number, is the note when it is highlighted) and is never changed by the program; put the files there by hand if you like (.tsv, .dat, .txt, two or three numeric columns). A run copies the folder, model-settings.json and model-references.json, into its run folder with the other inputs (the curves as reference-fit-<file>).

  • A wrong file or wrong columns is a warning, never a stop. The note line says so while the columns are chosen and again after the import: sigma is about I: a fit file? wrong file? (the sigma column of a measured curve is as big as I(q) and follows it: a SASBDB .fit file read as q, I, sigma, whose third column is the model); for a reference fit, same numbers as the data: the model column?, 5.2x off the data: wrong column? (the median distance from the measured curve on its q) or q range does not meet the data: units?.

  • The reference curve of one model. On the models list ^f (reference) opens the model's reference fit: model (its file), curve (one of the project's reference curves or none; left, right or Enter go through them), software (MultiFoXS 2-state), tag (fit3_model1), chi2 (the depositor's, with its method: MultiFoXS 2-state 0.79) and rescale (scale the curve onto the data by least squares, for a normalized fit). Every change is saved at once into <project>/model-references.json ({"<model>": {"tag", "software", "ref_chi2", "fit", "rescale"}}, sparse; the columns and units of the curve were chosen when it was imported). A run then draws, on that model's figure (<model>_comparison.tex), the data, the reference curve (software tag (chi2) in the legend) and the MAP curve with its own χ², and writes ref_chi2 in the model's LOG.

A project can run only with valid data and an energy. A data file that cannot be used is told, never written over, and r puts it aside as .corrupt.

Buffer

buffer is a small page with up to five rows, buffer (N solutes), custom solutes (N), load a recipe, new recipe and, for a buffer that has solutes, save current recipe globally, and a one-line status of each file (buffer: none yet, pH not set, buffer: unusable!). r on an unusable file offers to reset it.

Recipes are named buffers kept in the data folder (recipes.json, shared by every project). save current recipe globally asks a name (replace "NAME"? if one has it) and saves the buffer as it is on disk, with its pH and σ. load a recipe lists the saved recipes with their solute counts (type to find one: the list narrows as you type; ^r deletes the highlighted one, after a question) and opens the buffer table with the recipe's rows as unsaved ones (*); the recipe's pH, σ and temperature, when it has them, come in as an unsaved change of the pH row (a recipe without leaves the buffer's own; one without a temperature leaves the buffer's temperature). At the first ^w a buffer that has solutes asks replace N solutes with recipe "NAME"?. new recipe opens the table empty and replaces nothing before ^w. Nothing is written before ^w; the recipe is copied, not linked. The unit ^k is not part of a recipe. Global settings has two more options under the four groups: recipes (y) and solutes (t) open the recipes table and the custom solutes table; r on an option whose file cannot be used offers to reset it (the old file stays as <name>.corrupt). In the recipes table, the custom solutes table and the buffer table, / finds a row by name (type part of it, ⏎ puts the cursor on it) and s puts the rows in alphabetical order (shown only while they are not); the recipes and the custom solutes also open in that order. The r reset legend shows only on the row whose file cannot be used. The path prompts (data, reference fit, models) are boxed like the other dropdowns. Template recipes (2026-11-12). A recipe can be a template: it keeps its definition inside the recipe ("template" in recipes.json), so that what depends on the pH and the temperature is worked out when it is loaded. Three kinds: builtin (a shipped buffer: concentration, ±, titrant, pH set at, rest of the recipe), custom (your own buffer: 1 to 3 pKa steps with the pKa at 25 °C, d(pKa)/dT and the charge of the acid form, a titrant acid or base with its ion, concentration and ±; run by the same engine, labelled constants not sourced) and table (amounts of each row at two or more pH, interpolated linearly, a pH outside the points refused). The recipe's solutes are its fixed rows (salt, protein, ...). Make one with shift+t on the recipes table (a name, then the questions) or on the buffer table (the rows come in linked and follow the pH and temperature), or save a buffer whose rows follow one template with save current recipe globally (it asks save "NAME" as a template?; Enter saves the template, n a plain recipe, Esc saves nothing; rows of two templates cannot be one). The recipes table has a template column while one exists. Loading a template recipe adds its fixed rows and the rows of its definition at the recipe's pH and temperature (else the buffer's; no pH at all asks you to set it first), and they follow the buffer table's pH and temperature (a table outside its points leaves the rows as they are and says so). A definition that does not check makes the recipe invalid: its fixed rows load and the problem is the hint (editing the template fixes it). shift+e on the recipes table edits the definition of the recipe under the cursor: the wizard starts from it, every question prefilled, Esc leaves it unchanged. shift+v on the buffer table turns its rows (bundled and custom non-biological solutes that do not follow a template yet) into a table template: they are the first point, at the table's pH, the wizard asks the other pH and the amounts there, and the rows come back linked in place of the typed ones (save the buffer as a template to keep it). The wizard takes your custom solutes wherever it takes a solute (a custom buffer's solute, the rows of a table); the definition then holds a snapshot of the solute (z, pmv, sigma-pmv), so it needs no custom file. Julia never sees a definition (it reads rows only; a row's template key is ignored). Notes (2026-11-11): a project, the buffer and every recipe can carry titled notes, "notes": [{"title", "text"}] (absent when there are none; no limit on the number or the length; a title is 1 to 40 characters, unique without regard to case). shift+n opens the notes list: notes: shift+n in the project menu's taskbar (written to project.json at ^w, and copied into every run's archive), on the buffer table and on a recipe's own table (notes save by themselves, at once, into buffer.json or the recipe: only the solutes and the pH wait for ^w); shift+n on the recipes table opens the highlighted recipe's list. The list: Enter edits a note, ^n a new one (asks the title), ^e renames, ^r marks it to go, ^w saves. The editor is built in (arrows, home, end, page up and down, Enter, backspace, delete, paste; lines scroll sideways, they do not wrap): ^w saves the note through the list's save at once (a project writes project.json; the buffer or recipe takes it as an unsaved change of its table), Esc and ^x save a changed text and leave: nothing is dropped. Saving the buffer as a recipe copies its notes in when it has any (else a replaced recipe keeps its own); loading a recipe brings its notes in as an unsaved change (the replace question then says and notes). The recipes table has the columns name, solutes, kinds (3 solute 1 polymer 2 custom 4 seq), pH, σ (blank for a recipe without) and notes (their titles); Enter asks the name (prefilled: the rename) and opens the recipe's own solutes table (its pH row too); ^n a new recipe, shift+n its notes. Buffer templates. shift+b fills the rows of a standard buffer the way the fitting scripts do by hand: the buffer's own row at the concentration you typed, plus the counter-ion that setting the pH adds (chloride for Tris and the other amine bases titrated with HCl; sodium or potassium for the others, with NaOH or KOH; polyprotic buffers such as phosphate and citrate as their salts). Structure files. The run archive

When Julia has finished (a run that is done, failed or aborted) the program packs the run folder: the screen says packing, then done. EVERYTHING of <run>/ goes into ONE 7z archive beside the folder, runs/<run>.7z, and the folder is removed: run.json, the workbooks, the logs, the inputs and the plots, as FLAT names (run.json, run.LOG, plots.txt, settings.json, ..., <model>.LOG, <model>.xlsx, <model>.tex, <model>-plots.txt, <model>-76x10.txt, compare.tsv, compare.tex, compare-plots.txt, ...), at the best compression (-mx=9). The run's name is the same with or without the archive, a run that is still going (or whose pack failed) is the plain folder runs/<run>/, and the readers take either; run.json of an archive is read once and kept while the archive stays as it is, so the run list stays fast. A workbook goes into the archive as the tree of its unzipped XML files (m.xlsx as m/[Content_Types].xml, m/_rels/.rels, m/xl/...), which 7-Zip compresses much better than the zip it already is; the archive is packed with the highest settings (x=9, word size 273, solid, all from run_flow.json). A workbook that is only in the archive is zipped again from its tree into a proper .xlsx ([Content_Types].xml first, deflated, the same bytes every time) in a copy in a temporary folder that is removed when the program ends; files moved to the data folder are always proper .xlsx files.

The pack is atomic: the archive is made as <run>.7z.tmp.<pid>, tested with 7z t and compared with the list of what was packed, and only then renamed to <run>.7z; the packed originals are removed after that and never before. If anything fails (a full disk, a failed test) the run folder stays exactly as it was, the staged file is removed, and the note row on the run screen says why (not packed: ...); the run's own outcome is unchanged. While a pack runs, deleting that run is refused with this run is being packed.

Reading is the same for packed and plain runs. The viewer's plots (^p), run.LOG (^l and view run.LOG), the logs menu (every view, conditions, the restores) read the archive or, for a run that was never packed, the plain folder; the plots are read straight out of the archive (nothing is extracted to disk), always read-only, with a check of every entry name (no .., no absolute path) and a size cap per entry. Extracting (move and compile plots) uses a temporary folder that is always removed. The archive is made by 7-Zip (the 7zip-bin binary, run through node-7z; a 7z, 7zz or 7za on the PATH is the fallback when the bundled one cannot run).

Two copies at once

Two copies of the program, or the program and a Julia script, can use the same data folder safely. Saving takes a short lock on the file. Settings changed in two copies are merged (the same setting: the last save wins). A buffer or custom-solute list that another copy saved meanwhile is not overwritten (changed on disk: reopen it). A project deleted in one copy is not brought back by the other. Starting a run takes a lock too, so two copies starting at the same instant cannot both win; a refused start says a run is in progress (pid N), and delete run and delete project refuse a live run.

For contributors

The interface only reads and writes the project's JSON files and starts programs; Julia knows nothing about it. run_project (Julia, src/store/run-project.jl) is the one entry the interface calls, with the arguments project_dir, temperature, ui = :tui and run_dir; the same JSON files are read by Julia's load_settings and load_buffer (in src/store/*.jl), and the test fixtures test/fixtures/settings/*.json and test/fixtures/buffer/*.json at the repository root are shared by both sides, so a change to a file format changes both.

The Julia side of the interface

The Julia that only the interface needs lives in tui/src/store/, next to its TypeScript twin, and is not part of the BAYSOL package: run-project.jl (twin: run.ts, projects.ts) defines the module BAYSOLRun and includes settings-file.jl (settings.json and model-settings.json, twin settings-store.ts), buffer.jl (buffer.json, twin buffer.ts) and model-references.jl (model-references.json, twin references.ts). The module does using BAYSOL and reaches what BAYSOL.Pipeline does not export through a short import BAYSOL.Pipeline: ... list, so the package keeps only the fit, its outputs and the keyword side of the settings (seed_keywords, run_keywords, results_keywords, InvalidSettingsError). The interface starts it as julia --project=<repo> -e 'include(ARGS[1]); BAYSOLRun.run_project(...)' with the path of run-project.jl (runProjectFile in run.ts). Its tests are tui/test/*.test.jl (bysl unit run-project, buffer.test, settings-file.test), run by the same runner as the Julia unit tests, with the shared fixtures in test/fixtures/. The sections below are the contracts of these files.

The settings of the user

The terminal interface keeps the settings a user changed in settings.json in the BAYSOL folder (settings_file() of BAYSOLRun: $BAYSOL_HOME, else baysol in the data folder of the system). load_settings() reads it and gives the value of every setting, the saved one or the default, in the type the default has (an Int, a Float64, a Tuple, and so on); a missing file gives the defaults. Nothing illegal gets through: every saved value is checked before it is used, against its type, the SETTING_LIMITS and SETTING_CHOICES of its Params.jl, a colour that exists, the shape of a tuple, and the SETTING_RELATIONS that tie settings together (MODE_δρ₁₂ strictly inside BOUNDS_δρ₁₂, SASA_N_OCC at most SHELL_SAMPLE, an opacity between 0 and 1, ...). A file that cannot be read, or one invalid value, prints a warning for each problem and throws an InvalidSettingsError, so the fit that asked for the settings does not start. The terminal interface makes the same checks (on the same data, bysl harvest defaults writes it) each time a setting is saved, a sheet is opened or a project is opened; there an invalid value is wiped, back to its default, and the setting says so. The entry points seed_model, run_model and results of BAYSOL do not read the file themselves: run_project passes them what load_settings returns, as keywords (BAYSOL.seed_keywords, run_keywords, results_keywords).

The buffer of a project

load_buffer(path) reads the buffer.json that the terminal interface keeps in a project (concentrations in mM as typed) and returns the Vector{Solute} that seed_model takes, in file order, with the concentrations and their uncertainties divided by 1000 (mol/L). A missing file is an error (InvalidBufferError): BAYSOL does not guess a buffer, since a run on pure water by accident is worse than a stop. A file with no solutes is accepted with a warning (the buffer has no solutes: pure water). The file is an object with a solutes array; the schema is frozen in test/fixtures/buffer/buffer.json, which the interface's tests and buffer.test.jl share:

kindKeys besides mM, sigma-mM (required; mM above 0, sigma-mM at least 0)Solute
"nonbiological", "polymer"arg (table name; grade or family string)NonBiological, Polymer
"dna", "rna", "protein"arg (the clean sequence)DNA, RNA, Protein
"custom-nonbio"custom (name), z, pmv, sigma-pmv (null = the fallback)CustomNonBio
"custom-polymer"custom (name), units (1 to 4 of z, slope, sigma), counts (one per unit), z-ends, pmv-ends, sigma-ends (null = none)CustomPolymer

The file also holds the pH of the buffer and the standard uncertainty of it, "pH" and "sigma-pH" next to solutes (the terminal interface calls the second one σ), and the optional "temperature" in °C (0 to 100, validated when present, not returned by load_buffer_ph: the run script takes the temperature as its argument from the interface). They come as both or neither: a pH from 0 to 14 and a sigma-pH from 0 to 14 (the limits are BUFFER_PH_MIN and the like, the same numbers as tui/assets/data/buffer_conditions.json). load_buffer checks them when they are there and does not need them; load_buffer_ph(path) returns (pH = ..., σ_pH = ...), the pH and σ_pH of seed_model, and throws an InvalidBufferError when the buffer has none, because a run needs a pH.

name, source, record and a unit's label and formula are labels only. The loader checks the shape (kind, keys, types, the concentration, the list lengths) and prints a warning for each problem before it throws one InvalidBufferError that lists them with 1-based row numbers; the ranges of the numbers (electrons above 0, a finite volume, a chain of at least 2 units) are refused by ρₑ, not repeated.

The run of a project

run_project(project_dir; temperature, ui = :cli) fits every model of a project folder in one process and writes the run folder <project>/runs/<stamp>/ (stamp is the local time, the zone label, the offset from UTC and the date, HH-MM-SS-mmm_TZ_±HHMM_YYYY-MM-DD, e.g. 23-35-29-123_EST_-0500_2026-11-07: only digits, letters, hyphens and underscores; the zone label is the platform's Libc.strftime("%Z") when it is 3 or more Unicode letters (accents kept, whitespace removed), else the zone's name from TZ or the /etc/localtime link (Istanbul, SaoPaulo), else LOCAL, never GMT or UTC as a stand-in; run.json times stay ISO-8601 UTC; macOS and Windows untested). It is what the terminal interface starts as a child process; it knows nothing of the interface and can be started from any shell. The project holds settings.json (what load_settings reads: the settings of this project; missing means the defaults), buffer.json (the solutes with pH and sigma-pH, read by load_buffer and load_buffer_ph), data.tsv (three tab-separated columns q, I, sigma, no header) with data.json (units, "nm-1" or "A-1": q is divided by 10 for "nm-1"; energy, the X-ray energy in eV; other keys such as mapping are ignored) and models/ (.cif and .pdb) and, optionally, reference-fit/ and model-settings.json and model-references.json (below). The temperature (°C) is the buffer's; it has no uncertainty.

  • The inputs are copied into the run folder first and the run reads only the copies (solutes.json is made from them: every solute with its electrons Z, partial molar volume and uncertainty at this pH, custom solutes as their snapshot, a sequence as its length and first residues, and the buffer's rho_e), so editing the project during the run changes nothing. A file already there (a caller that took its own snapshot under its locks) is used as it is.
  • The folder is claimed with a non-recursive mkdir (when the stamp exists, the next millisecond), after a check that no run of the project is live (running, a heartbeat under 60 s old, and the pid exists on this host: otherwise a run is in progress (pid N)). A caller that claims it itself passes run_dir.
  • run.json has one writer, this function, which replaces it atomically (a temporary file renamed over it) at every change and every 10 s (heartbeat). The run folder, the keys and the states are a protocol with the interface (RUN_* constants in run-project.jl are guardrails, not settings).
  • Failures do not stop the loop. An exception while fitting one model (a missing form factor or radius, an unresolved residue, a run that did not converge) is caught, its message and stack go to the ERRORS section of run.LOG, the model is failed and the next one starts (the line on stderr is short, model <name> failed: <reason>, with not converged for a NotConvergedError and else the first sentence of the message cut to 50 characters; run.json and run.LOG keep the whole message); an invalid input (buffer, settings, data) fails the run before any model. The run ends failed if anything failed and done otherwise. Ctrl-C, SIGTERM and, with ui = :tui, the end of standard input (the interface died: the process exits, nothing is left over) end it as aborted, the files finished (the running model aborted, the rest skipped).
  • ui = :cli prints the plots as well as writing them; :tui never prints them (plots.txt only, and the other sizes below). The log, the summary of each fit and the sampler's output always go to stdout/stderr and are copied into run.LOG.
  • The plot folder and the LaTeX compiler (the settings FIGURES_DIR and FIGURES_COMPILER, the keywords plot_dir and latex_compiler of results, the kind path: text without control characters, empty for "not set", at most 4096 characters). With a plot_dir that is not "", results also copies its .tex figures into that folder (made if missing, a file of the same name replaced; the copies are not in the files returned). run_project gives each model the place <plot dir>/<project>/<run>/<model>/ in it (one folder for all projects; the terminal interface's own "move tex" and "compile plots" put the files flat into the plot dir instead, named for the model, a taken name getting -2, -3, and never replacing a file; its default, when the setting is empty, is the plots folder of the BAYSOL data folder, and a Julia run with the setting empty copies nothing). The data folder (the setting TABLE_DIR, the keyword table_dir of run_project, the kind path, a setting of the whole run): when it is not "", run_project also copies the workbook of each model that finished (<model>.xlsx) and the comparison table (<project>-compare.tsv) into it at the end of the run, a taken name getting -2, -3, ... (all the files of one unit together) and never replacing a file; the terminal interface's "move data" uses the same setting (its default, when empty, is the data folder of the BAYSOL data folder). latex_compiler is the path of the compiler that compile = true runs (lualatex, xelatex or pdflatex, named by its file, .exe allowed): that compiler and no other is used, and a path that is not a file or not one of the three is an error (a warning of the failed figure, as any failed LaTeX run); a font needs lualatex or xelatex. "" keeps the old rule: with a font lualatex, else xelatex, without one the first engine PGFPlotsX finds. Both are settings of the whole run, not of one model. compare_results does not take them.
  • The terminal plots at several sizes (ui = :tui; the setting PLOT_TUI_SIZES, the keyword plot_tui_sizes, the kind sizes). A text plot cannot be resized afterwards, so a viewer that has to fit a window needs it drawn at several sizes beforehand. Besides <model>-plots.txt, which keeps the size of PLOT_PREVIEW_SIZE and is exactly what it always was, the run writes <model>-<W>x<H>.txt (and compare-<W>x<H>.txt) for every pair (W, H) of PLOT_TUI_SIZES: the same text as <model>-plots.txt (a title line above each boxed plot, a blank line between), W the width in terminal columns of the WHOLE plot (axis labels, ticks and legend included: the drawing is made at an area width that is corrected until its widest line is W) and H the rows of the plot area (the title, the borders, the ticks and the label add 5 rows to a curve plot; a histogram has about H bins and is cut down until it is at most H + 5 rows). The default is ((76, 5), (100, 9), (130, 13), (170, 18)): the smallest is 76 columns by 10 rows, which fits a window of 80 by 24. A list is valid when it is non-empty, every size is at least 24 by 3 and at most 400 by 100, and each size is larger than the one before in both width and height (the message is PLOT_TUI_SIZES = ...: must grow in both width and height...); in settings.json it is a list of [width, height] pairs. A plot whose labels need more room than the request (the residuals plot needs about 60 columns, a legend with long names more) is drawn as wide as it needs and cannot be cut, so the file's real size is measured: each model's entry of run.json, and the compare entry, has plot_sizes: [{file, width, rows}] in the order of the setting (file in the run folder, width the widest line in terminal cells, as a viewer counts them, a braille blank U+2800 being one cell, rows the lines of the tallest plot in the file), the empty list with ui = :cli (which prints the default size only). The drawing at all sizes costs about 5 ms for the nine plots of a model once the code is compiled (about half a second more for the first model of a process). Measured on the crambin fixture (the fit and residuals plots, and the seven histograms; rows of the tallest): requested 76 by 5 gives 76 columns and 10 rows, 100 by 9 gives 100 and 14, 130 by 13 gives 130 and 18, 170 by 18 gives 170 and 23.
  • The reference curve of single models (model-references.json). A deposited entry has one fit file and one χ² for each atomic model; <project>/model-references.json gives them to the models: {"<model>": {"fit": "SASDCQ2_fit3.tsv", "software": "MultiFoXS 2-state", "tag": "fit3_model1", "ref_chi2": "MultiFoXS 2-state 0.79", "rescale": false}}, every key optional, the model its file stem. fit names a file of reference-fit/ (q in the units of data.json, as the other references), software and tag label it (software tag, the file's name without both, (rescaled) added with rescale), ref_chi2 is the depositor's χ² with its method and rescale scales the curve onto the measured one by least squares (a normalized fit). The model's results call gets the curve as its references and the text as ref_chi2, so its comparison figure <model>_comparison.tex (and <model>_comparison in the workbook) draws the data, the curve (label (ref_chi2) in the legend) and the MAP curve (BAYSOL MAP χ² = ...), and the model's LOG has the ref_chi2 row. A file that cannot be read, a value of the wrong kind, an unknown key, a fit that is no file of reference-fit/ and a name that is no model of the project are notes in the ERRORS section and are skipped; they fail nothing. The file is copied into the run folder with the other inputs. The combined comparison of the run keeps drawing every curve of reference-fit/.
  • Settings of single models (model-settings.json, the keyword model_settings). A model may be fitted with settings of its own, on top of the project's: the file <project>/model-settings.json holds {"<model>": {<sheet>: {"<SETTING>": {"value": ...}}}}, the shape of settings.json for each model (the model is its file stem, the sheet names are free and only group the entries), read and checked as settings.json is (every value against its type and limits, then the rules between settings on the model's whole set). It is sparse: a model or a setting that is not in it is the project's. The keyword model_settings is a Dict or NamedTuple from a model name to a Dict or NamedTuple of keywords (model_settings = (; crambin = (; q_max = 0.3, n_chains = 8))) and wins over the file; nothing clears a setting that may be nothing (q_max). The order of strength is model_settings, the file, the keywords of the call (q_max = 0.3 for every model), settings.json, the default: a model that gives a setting of its own keeps it whatever the call says for the project. Which settings: every one that belongs to a fit (the data selection Q_MIN, Q_MAX, SIGMA_SCALE, EXCLUDE_Q, the structure CHAINS, MODEL, ADD_HYDROGENS, LMAX, the model, shell, bead and prior settings, the sampler and the MAP search, RNG_SEED, VAL_SIGMA, TARGET_ACCEPT, N_CHAINS, N_ADAPT, N_DRAWS). Not per model (RUN_LEVEL_SETTINGS in settings-file.jl, and every PLOT_*): TABLE_SIGFIGS, FIGURES_TEX, FIGURES_COMPILE, FIGURES_FORMATS and all the PLOT_* settings (the look of the figures, PLOT_COMPARE and its colours, markers and line width, PLOT_TUI_SIZES); naming one in a model's table, or as a keyword of model_settings, whatever its value, is an InvalidSettingsError that names the file or keyword, the model and the setting (model-settings.json, model B: PLOT_COMPARE is a setting of the whole run, not of one model). A test checks the list against the kinds of the catalog, so a new setting has to be classified. An unreadable file, an invalid value, a broken rule (a model's Q_MIN above the project's Q_MAX) fails the run before any model starts, like an invalid settings.json; a name in the file that is no model of the project (renamed or removed) is a note in the ERRORS section and is ignored; a keyword that is no setting's, or a table of the wrong shape, is an ArgumentError at once. The file is copied into the run folder with the other inputs. Each model's LOG has a setup row override_<setting> (lower case: override_q_max) for every setting it was given of its own, a failed model's LOG too, and its run.json entry overrides lists their names (["N_CHAINS", "Q_MAX"], sorted; empty for none). The buffer and the temperature are the project's: they are not per model, so the solutes.json snapshot is made with the project's PMV_FALLBACK_UNCERT. The comparison and its workbook stay valid when models were fitted to different data selections: every curve is drawn over its own q range and interpolated onto the measured grid only where it reaches (empty cells elsewhere).
  • n_samples, n_adapt, sigma, rng_seed, n_chains, retry, add_hydrogens and lMax (per model: see "Settings of single models" above) default to the project's settings (N_ADAPT + N_DRAWS, N_ADAPT, VAL_SIGMA, RNG_SEED, N_CHAINS, ADD_HYDROGENS, LMAX) and the defaults of run_model; the data and structure keywords (q_min, q_max, sigma_scale, exclude_q, chains, model) come from keywords or settings.json only (the project's data.json does not hold them yet); the seed keywords and the plot style come from the settings too. The other sampler settings are constants the sampler reads and are not applied per run.
  • Reference fit. The optional folder <project>/reference-fit/ holds the reference curves the comparison draws: every .tsv, .dat or .txt file (any case of the extension) with two or three numeric columns (q in the units of the project's data.json, I, and an optional σ that is read and not used), separated by white space, tabs, commas or semicolons, is one curve named by its file stem (CRYSOL.tsv is CRYSOL; a taken stem gets -2). Blank lines, everything after a # and text lines before the first numbers (a header) are skipped. The files are copied into the run folder as reference-fit-<file> with the other inputs (an interface that took the snapshot itself has put them there) and read from there, q divided by 10 for "nm-1". A file that cannot be read (a cell that is no number, other than 2 or 3 columns, no usable point) is skipped and named in the ERRORS section of run.LOG with its line, as a note: it never fails the run or changes its status. Without the folder the comparison has the models and the measured curve alone.
  • The comparison. After the last model, when plot_compare is on (the setting PLOT_COMPARE, default true) and at least one model finished (one is fine: the data, its fit and the references), compare_results draws every finished model, the references and the measured curve (see "The comparison figure") into the run folder: compare.tex, compare.tsv, and compare-plots.txt (the terminal plot as plain text, also appended as === compare === to plots.txt; printed to the terminal with ui = :cli, never with :tui; with :tui also compare-<W>x<H>.txt at the sizes of PLOT_TUI_SIZES). run.json then has a compare entry, {status: "done"|"failed", files: [names in the run folder, thecompare-<W>x<H>.txtnot among them], models: [names], references: [names], plot_sizes: [{file, width, rows}], error}; the key is absent when no comparison was made (the switch off, no model finished, an interrupted run). A failure of the comparison is caught like a model's: a note in the ERRORS section, compare.status "failed" with its error line, and the run's status unchanged. A model cannot be named compare or run (the comparison's and the run's own files have those names): it gets compare-2, run-2.

Layout of tui/src (four folders):

FolderWhat lives there
core/no UI: environment.ts (folders, the cache, asset lookup, the RUN_FLOW and LOGS_FLOW constants, the Julia command), terminal.ts (text width, wrapping, number parsing, hasTerminal), file-system.ts (JSON files, atomic writes, locks), archive.ts (7-Zip: atomic packing, read-only listing and reading of entries, extraction into a temporary folder), fonts.ts
store/the data layer, no React: settings, projects and the run folder, buffer and solutes, the add flow, custom solutes, data import, the run session and its logs, the run archive (run-archive.ts), the plots actions (plots.ts), the viewer's data
ui/the kit every screen is built from: interaction.tsx (the navigation stack, all key definitions, text input, cursor lists), theme.tsx, grid.tsx (menus and legends), input.tsx (prompts, dropdowns, questions, the theme picker), frame.tsx (the screen frame and forms)
screens/the screens: menus, data, solutes, custom solutes, settings, the run screen, the viewer and open runs

main.tsx is start-up only (it needs a terminal, sweeps stale runs, installs the SIGHUP and SIGTERM handlers); app.tsx is the App component (theme, size guard, the Ctrl-C handler, the navigation stack). assets/ has the logos, the menu pictures and the data files (setting_sheets.json is the settings sheets).

Architecture in short. Every key goes through one route: a screen calls useKeys(handler, active) and the handler asks press.is(keys.x); keys are defined once in ui/interaction.tsx (and the menu hotkeys in ui/grid.tsx), never spelled elsewhere, and legends are built from the same definitions, so the hint can only list keys that work. State lives in store/; a screen is a thin view. A run is a Julia child process in its own process group, started by RunSession after the claim of a run folder under a lock; run.json has one writer (Julia) and liveness is status running plus a heartbeat under 60 s; the session aborts the group with SIGTERM and a grace time, then SIGKILL.

Commands (from tui/, or the repository root with -w tui):

npm start       # run it
npx tsc         # type-check (strict, no emit; also `npm run check`)
npm test        # the node:test suite (tsx --test test/*.test.ts); takes minutes

Formatting and lint are the repository's: bysl fmt runs Biome (installed at the root) and the TypeScript whitespace rule, bysl fmt --lines fails on a line over 92 columns or an indentation that is not a multiple of 4 (exactly 4 spaces per level, continuation lines too), and bysl precommit runs everything before a commit. Every source file starts with # SPDX-License-Identifier: LGPL-3.0-or-later in its comment syntax (bysl fmt adds it).

Tests. Pure logic is unit-tested with node:test (test/*.test.ts); the run flow is tested with real processes (concurrency.test.ts: two processes claim a run, exactly one wins; a killed child becomes interrupted) and a stand-in for Julia, test/support/fake-julia.ts (modes done, failed, hang, ...; the environment variable JULIA=<script> makes the whole program use it). Tests never touch your data or cache folders: they use throwaway ones.

Checking a screen by hand. Screens have no render tests; drive the real program in a pseudo-terminal: start npm start with BAYSOL_HOME and BAYSOL_CACHE pointing at scratch folders, a window size of 80 x 24 set with TIOCSWINSZ, wait a few seconds for the start, feed keystrokes, and read the screen with a terminal emulator library (for example Python's pty and pyte). Decode the output as a stream (a multi-byte character can be split between reads). The blocks in this guide were captured that way. Never point such a run at the real data folder.

The earlier Clojure interface is gone; tui/SPEC.md is its specification, kept as the reference of the rules, numbers and messages the TypeScript version preserves.
