BAYSOL terminal interface

The terminal interface (TUI) is a full-screen program for using BAYSOL without writing code: you make a project, put its 3D model, its measured curve and its buffer into it, press one key to fit, and read the results in the same window. It is written in TypeScript with Ink (React for the terminal) and runs in any terminal of at least 80 columns by 24 rows; nothing has a fixed width, lists scroll and text wraps. It looks best with 24-bit colour. The fit itself is the Julia package: the interface starts Julia as a child process, shows its output live, and reads the files it writes.

This page is the user guide and the reference; the last section is for contributors. The same steps, shorter, are in the first guide of the repository's main README.

Install and start

You need Julia 1.12, Node.js 22 or newer (node --version) and a BAYSOL folder that contains tui/. The repository has one node_modules, at its root: tui is an npm workspace of the root package.json.

cd BAYSOL                  # the repository root
npm install                # once, here, not in tui/
julia --project=. -e 'using Pkg; Pkg.instantiate(); using BAYSOL'   # once: the fitting code
cd tui
npm start                  # every time (runs `tsx src/main.tsx`)

The julia line downloads and compiles BAYSOL (several minutes) so that the first fit is not the one that waits; a first fit also downloads the helper programs PROPKA and pdb2pqr and needs internet. A run starts julia --startup-file=no --color=no --threads=auto,1 --project=<repository root> ...; the program is julia on the PATH, or the one named by the environment variable JULIA.

Started with no terminal (a pipe, a launcher) the program prints BAYSOL: this program needs a terminal and stops. Made smaller than 80 x 24 it shows a message in place of the screen and returns to the same screen when the terminal is big enough again. The release name on the main menu comes from the repository's Project.toml.

The data folder holds everything you make. It is chosen like this:

SystemData folderCache of downloaded structures
any, if BAYSOL_HOME / BAYSOL_CACHE is an absolute path$BAYSOL_HOME$BAYSOL_CACHE

A relative path in an environment variable is ignored. The folders are made on first use. The cache can be deleted at any time; it is rebuilt when needed. To try the program without touching your real work, start it as BAYSOL_HOME=/tmp/baysol-try BAYSOL_CACHE=/tmp/baysol-try-cache npm start.

The macOS and Windows parts (the desktop file chooser, also of the references, opening a folder in the file manager, stopping a run on Windows) are written from the systems' documentation and are untested. The rest behaves the same everywhere.

A first session in ten steps

  1. npm start. On the main menu press n, type demo, press Enter: the project menu opens.
  2. m (models): paste the full path of a .cif or .pdb, press Enter. ^x goes back.
  3. d (data), load a file: paste the path of your curve, Enter; check the three columns in the preview; press ^w.
  4. On the data screen, set units (Enter turns nm⁻¹ and Å⁻¹) and energy (eV).
  5. ^x, then b (buffer), Enter on buffer: ^g for the pH (7.4 0.1), ^n for each solute (name, concentration, ±; ^k turns the unit), ^w to save.
  6. ^x to the project menu. A run: shift+r item appears at the bottom once everything is there.
  7. Press Shift+R, accept or change the temperature, press Enter.
  8. Watch the run screen. When it says done, press Enter.
  9. o (open...), open runs, Enter on the model: the results workbook. ^p shows the plots.
  10. ^l on a run reads its log; ^x goes back; ^x again and q on the main menu quits.

Screens and keys

Moving around

Move with the arrow keys and press Enter, or press the hotkey of an option. The hint at the bottom lists the keys that work from where the cursor is, and nothing else; the footer's height depends on the screen only, so the logo at its left never jumps. The table-style screens (the buffer table, the custom solutes table and forms, the settings sheets, the logs pages) are blocky: the blocky logo, double-line tables, the footer in a double-line box. Every other screen is smooth: the rounded logo, rounded panels, thin single-line tables.

  • Esc closes what is open (a prompt, a list, a question, a pager). It never quits and does nothing at menu level.
  • Ctrl-X goes back one screen, from any mode. It never quits.
  • q on the main menu, Ctrl-C and Ctrl-D are the only ways to leave the program. Ctrl-C and Ctrl-D first stop a run that is going, then leave.
  • Ctrl-T opens the theme list on any screen (also during a run).
  • ^s, ^q, ^z and ^y are taken by the terminal; ^m, ^i, ^j arrive as Enter, Tab and Enter.
  • Unsaved changes ask (discard N changes?: Enter discards, Esc keeps) when you leave a screen with unsaved changes. Removing anything you made asks (delete X? this cannot be undone!: Enter deletes, Esc keeps).

The theme list (^t)

All 20 themes at once, alphabetical, each with an emoji, four colour swatches and its mode: abyssal, arboreal, autumn, citron, graphite, holograph, invert, lavender, luxe, mate, onigiri, pamplemousse, parchment, rose, syrah, terracotta, tweedia, ultrapink, ursus, vt100 (ten light, ten dark). Arrows move, Enter picks, Esc or ^t leaves. The pick is saved by name in theme.json and is the theme of the next start; the bottom right of every screen reads theme (^t): <name> <emoji>. The program only paints cells; it never changes your terminal's own colours.

Models

models takes the full absolute path of a .cif or .pdb file. Names are hinted as you type and Tab completes. The file is copied into the project's models/ folder (copied lyz.cif); the original is never touched, and an existing name is never overwritten. A project can hold several models; a run fits each in turn.

KeyDoes
o (on an empty field)pick files in the desktop file chooser
m (on an empty field)list the project's models (models (N): m)
^r or Delete (on the list)delete the highlighted model after a question
^o (on the list)the settings of the highlighted model (below)

Settings of one model. On the list ^o opens the settings of the highlighted model: the same sheets as the project's, but only the settings that can differ from model to model (output has only VAL_SIGMA and plots is not offered: the figures' look, TABLE_SIGFIGS and FIGURES_* are settings of the whole run, so a model cannot have them). The title says model: <name>. Every setting shows its value and, in the last column (headed here), overridden (the model's own, in the full colour) or inherited (the project's value, muted). Edit as on any sheet: a value that differs from the project's becomes an override, a value equal to it removes the override (so the file stays sparse), ^u undoes the change under the cursor and ^r (inherit group) gives the group the project's values again. ^w saves into model-settings.json of the project (only the changed settings of this model, under a lock, over the file as it is then; another copy's changes to other settings or models are kept). In the list a model with overrides has a * and the note under the list says overrides: Q_MAX, N_CHAINS. A model that is renamed or deleted leaves its table in the file (a run ignores it with a note); the program never removes it. An invalid value, or a setting of the whole run, found in the file is wiped when the model's sheet opens (one line in settings.log, model <name>: <SETTING>). An override stays when the project's own value changes later, even when it comes to equal it (only an edit to the project's value, or inherit group, removes it), unless the two then break a rule (a model's Q_MIN above the project's Q_MAX): that override is wiped.

Data

The data screen has five options: load a file, change the columns, units, energy, references. Before a file is loaded it says no data yet.

  • units: Enter turns the unit of q between Å⁻¹ and nm⁻¹ and saves it at once into data.json (the TSV is never rewritten). A new curve starts as Å⁻¹. Julia divides q by 10 when it reads nm⁻¹.

  • energy: the X-ray energy in eV, above 0, saved at once. There is no default.

  • change the columns reopens the import on the stored source with the stored choices. If the source file is gone it says source is gone: <name>; an old data.json without a mapping says no source recorded: load a file.

  • references opens the list of the project's reference curves (the depositor's CRYSOL or FoXS fit, ...) that a run draws in its comparison figure. They are the files of <project>/references/. The summary of the data screen says references 2 (name1, name2) when there are some. The list opens at any time, but adding needs data (import the data first), because a reference is in the same units as the data (units turns them for both). The list shows each curve's name, its points (those with q and I above 0, the ones a run draws) and its q range. ^n adds one: a path prompt as for load a file, then the same import screen with roles q and I(q) and an optional sigma (none by default for a file with two columns; a chosen sigma is written, but a run reads and ignores it), the units in its title, and ^w adds. Rows with q (or a chosen sigma) not above 0 are dropped as in the data import, at least 3 points are needed. The file written is clean: <name>.tsv, two or three tab-separated columns, no header. The name is the source's file name without its extension, with every character that is not a letter, digit, -, _ or . made _; a taken name gets -2, -3, ..., so nothing is ever overwritten. ^r (or Delete) deletes the highlighted one after the question. A file in the folder that a run could not read is listed as unusable (its reason, such as line 3: a cell is no number, is the note when it is highlighted) and is never changed by the program; put the files there by hand if you like (.tsv, .dat, .txt, two or three numeric columns). A run copies the folder, and model-settings.json, into its logs/ with the other inputs.

A project can run only with valid data and an energy. A data file that cannot be used is told, never written over, and r puts it aside as .corrupt.

Buffer

buffer is a small page with up to five rows, buffer (N solutes), custom solutes (N), load a recipe, new recipe and, for a buffer that has solutes, save current recipe globally, and a one-line status of each file (buffer: none yet, pH not set, buffer: unusable!). r on an unusable file offers to reset it.

Recipes are named buffers kept in the data folder (recipes.json, shared by every project). save current recipe globally asks a name (replace "NAME"? if one has it) and saves the buffer as it is on disk, with its pH and σ. load a recipe lists the saved recipes with their solute counts (^r deletes the highlighted one, after a question) and opens the buffer table with the recipe's rows as unsaved ones (*); the recipe's pH and σ, when it has them, come in as an unsaved change of the pH row (a recipe without leaves the buffer's own). At the first ^w a buffer that has solutes asks replace N solutes with recipe "NAME"?. new recipe opens the table empty and replaces nothing before ^w. Nothing is written before ^w; the recipe is copied, not linked. The unit ^k is not part of a recipe. Global settings, ^e opens the library: recipes (N) and solutes (N). The recipes table has the columns name, solutes, kinds (3 solute 1 polymer 2 custom 4 seq), pH and σ (blank for a recipe without); Enter asks the name (prefilled: the rename) and opens the recipe's own solutes table (its pH row too); ^n a new recipe, ^r deletes (after a question, at once), ^u undoes, ^w saves, ^x goes back.

Concentrations are in mM and ± is their uncertainty (headers [mM], ±[mM]). ^k turns the unit mM, M, µM, mM...: the headers, the cells, the prompt labels (µM:) and what you type follow it; the file keeps mM, and a cell that does not fit shows as 1.37e-1 (the digits that fit, never ambiguous). The unit is kept while the program runs; an unsaved draft is unchanged by the switch. A * marks a change that is not saved; ^w saves everything, ^u undoes the change under the cursor or a removal mark, ^r marks a row for removal (the mark goes at ^w), Enter edits a cell.

Sequences as text. The path: prompt of ^f and ^e takes a file path or the sequence itself. Text with a /, \, ., ~ or : is a path (an existing file is read; otherwise no such file or use a full path); anything else is linted as a sequence. A paste of several lines (a whole FASTA) or longer than the field is taken at once and counted (pasted 12 residues: enter takes them); Enter takes it, typing forgets it. One lint serves text and files: a > header line, spaces, line breaks and the numbers of a GenBank-style listing are dropped and letters are upper-cased; nothing else is repaired. A wrong character is an error that names it and its place (invalid residue '-' at 12, U is RNA, not DNA (at 4), T is DNA, not RNA (at 4), empty sequence); the letters allowed are the ones Julia accepts (DNA/RNA: ACGT or ACGU plus the IUPAC codes; protein: every letter, X and * count as no residue). Text with no header is one row, seq1.

Rows made from one file share its mM and ±; edit them afterwards. The params column shows n/a for a small molecule and the sequence (with its length) for a protein or nucleic acid. These rows are what is in the buffer blank: never list the molecule you measured.

The pH and its σ. Both are saved together in buffer.json (pH and sigma-pH, each from 0 to 14); a pH without a σ, or out of range, makes the file unusable. A buffer with no pH is not ready to run. The unit ^k turns (mM, M, µM) is kept in the same file as conc-unit (written at once, and with every save); a missing or unknown value opens in mM, and Julia ignores the key.

Custom solutes are your own non-biological solutes and polymers, kept in the data folder and offered by ^n (small molecules) and ^p (polymers) in every project. A name the built-in list does not know says no match (custom: buffer>custom solutes). The custom table has the columns name, formula, Z, PMV @ 25 °C and ±; a polymer shows its units by their labels (A:C2H4O B:C3H6O, Z 24A+32B+10, PMV 36.9A+53.1B+9). In the table, ^n opens the form of a small molecule:

 new custom solute · non-biological

 > name
   formula                C7H13NO3S
   Z                      102
   PMV @ 25 °C (cm³/mol)  118.4
   ± (cm³/mol)            (3.04)

name; formula, a chemical formula (NaCl, Ca(OH)2, CuSO4·5H2O, SO4 2-; D counts as hydrogen) that gives Z as soon as it is taken, to keep or to type over (a formula that does not change keeps the Z typed; an unknown element or a bad formula says so in the note and leaves Z to be typed); Z, the number of electrons; PMV, the partial molar volume at 25 °C in cm³/mol; and ±, its uncertainty (left empty, the fallback (3.04) is used, the PMV_FALLBACK_UNCERT setting). Under the fields the live preview says how the electrons add up and what BAYSOL will use. Enter edits a field, ^w adds the solute to the table, ^w again saves the table; Enter on a row edits it, ^r deletes it (after a question, at once).

 Z = 10 + 24·nA + 32·nB
 n = 10 of each: Z = 570, PMV = 909.5 cm³/mol, σ = 18.19 cm³/mol
 n = 100 of each: Z = 5610, PMV = 9014 cm³/mol, σ = 180.28 cm³/mol

A unit row is used when it has anything in it (the first always; clearing a row removes a unit); a used row with no label gets the one offered for its place ((A)). A unit's Z comes from its formula (a trailing ( )n is dropped, no charge), to keep or type over; its ± is absolute and blank shows (2%). The end groups have no default: their Z (or a formula that gives it) and PMV are required, the ± is optional. The preview gives the chain in words with your labels and, once everything is given, its Z, PMV and σ for 10 and for 100 of each unit (the rule of Julia's CustomPolymer). In the buffer, ^p offers the polymers by name next to the built-in grades and families, then asks the number of each unit (nA, nB, ...), mM and ±; Enter on such a row re-types the counts.

Every setting is on a sheet. A run that does not converge at the first pass is rerun once with RETRY_N_ADAPT and RETRY_N_DRAWS (2000 each by default), so a small N_ADAPT/N_DRAWS can end as a longer run; extra chains are also started at other optima (OPTIMUM_MIN_CHAINS), so a run can have more chains than N_CHAINS. RNG_SEED makes a run reproducible; VAL_SIGMA is the half-width of the reported interval in standard deviations; FIGURES_COMPILE (needs LaTeX) and FIGURES_FORMATS (pdf png svg) render the .tex figures.

  • Enter edits: a yes/no turns over; a colour is picked from a list (type to narrow, Tab completes, or type #rrggbb); anything else is typed on one line (Esc gives up): a number, the figure formats separated by blanks (pdf png), a font name as it is (empty is the default font; a font LaTeX cannot find is a warning of the run), a pair such as a colour and its opacity as darkorange, 0.15.
  • Three list settings are typed as one line and shown the same way. PLOT_COMPARE_COLOURS: colour names or #rrggbb separated by commas or blanks, #D55E00, #0072B2, red (the names of the colour list, lower case; at least one; repeats allowed; the first model has the first colour, and so on, starting again). PLOT_COMPARE_MARKERS: marker names of the catalog, o, square, triangle (o * square square* triangle triangle* diamond diamond* pentagon pentagon* star x + asterisk oplus otimes; an ordered list, not on/off). PLOT_TUI_SIZES: sizes of the terminal plots as 76x5, 100x9 (76 x 5 and × are read too; whole numbers, each 24x3 to 400x100 and larger than the one before in both). A wrong line is refused with a short message and stays on screen. In settings.json they are lists: ["#D55E00", "red"], ["o", "square"] and [[76, 5], [100, 9]].
  • The data and structure settings (project settings; the data screen shows nothing new): Q_MIN and Q_MAX are optional q limits in Å⁻¹ (blank, none or auto clears one; Q_MIN must be below Q_MAX, an error on both rows at save), SIGMA_SCALE multiplies the standard errors, LMAX is an optional whole number (blank or auto: automatic). EXCLUDE_Q is one line of lo-hi pairs separated by commas, 0.1-0.2, 0.5-0.6 (blank or none: no range; 0 <= lo < hi). CHAINS is the chain ids to keep as letters or digits separated by commas or blanks or written together (A B, A,B and AB are alike; case counts; a repeat is refused; blank or all: every chain). In settings.json they are null, [[0.1, 0.2], [0.5, 0.6]] and ["A", "B"].
  • * marks a change not saved, ! a setting that cannot be saved (its message stays until the next key). ^w saves them all, ^u undoes the one under the cursor, ^r resets the group to its default (in a project: to the global value).
  • Every value is checked as you enter it, and again at save and when a project opens. An invalid saved value is reset to its default (in a project: to the global value) with a note, and a line in settings.log beside settings.json says which value and why.

Run

The project must have a model, a buffer with at least one solute and a pH, and data with its energy. Then the project menu shows run: shift+r. Shift+R asks one thing:

temperature °C: 25

The range is 0 to 100 °C (a number, please / from 0 to 100 °C otherwise); the start value is the temperature of the newest finished run, else 25. There is no temperature uncertainty. Enter starts the run. If a run of this project is already going the start is refused with a run is in progress (pid N).

The run screen is a live view of the last lines of Julia's output (the full text is also written to the run's run.LOG); the plots are not shown here, they are in the results. The counter reads running 0:42, aborting, done, failed or aborted. Keys are locked except ^t and:

  • Ctrl-C or Ctrl-D: abort and quit the whole program. Julia is asked to stop (SIGTERM) and given a few seconds to finish its log, then killed. Julia prints a stack trace for the signal; it is not an error of the run.
  • at the end, Enter returns to the project menu. A failed run shows the first line of its ERRORS section in the note row.

The run works on a copy of the project's files made at its start, so editing the project meanwhile (even in another copy of the program) changes nothing. One run per project can be live. If the program or the machine dies, Julia ends its run when its input closes, and a running run whose heartbeat is over a minute old is marked interrupted by whichever copy of the program notices it.

Logs (logs, g)

logs in the project menu is for reading and restoring what a run used; open... > open runs (below) is for the results workbook and plots. It lists the runs, newest first (by the instant in the name; the screens show 23:35:29:123 EST -05:00 · 2026-11-07 for the folder 23-35-29-123_EST_-0500_2026-11-07, and runs made before this form, yyyyMMddTHHmmssZ, the same way with UTC; the zone label is the abbreviation of the zone (EST, CEST, TRT) when the zone has one that fits the offset of that moment, else the official name of its main city with its accents, SãoPaulo, Istanbul: never a stand-in such as GMT; the data come from moment-timezone and @vvo/tzdb, installed by npm install): the time, how it ended (done, failed, aborted, interrupted, unknown for a damaged run.json; * marks the live run, ! an interrupted one), its models and its size. The list refreshes every two seconds; project: <name> is at the top right. Enter opens the run's options (project: <name> · run: <run> at the top right). Nothing is deleted from the logs menu: a run is deleted in open... > open runs.

logs/run.LOG has flat name<TAB>value rows: the setup (with temperature_c, ph, sigma_ph, energy_ev), then the output, a --- result --- block and, if anything failed, an === ERRORS === section with each message and its stack. Nothing in a run folder is ever overwritten; the only deletion is the explicit delete run. A file that cannot be used is never written over: it is told, and r resets it, keeping the old one as <name>.corrupt.

Two copies at once

Two copies of the program, or the program and a Julia script, can use the same data folder safely. Saving takes a short lock on the file. Settings changed in two copies are merged (the same setting: the last save wins). A buffer or custom-solute list that another copy saved meanwhile is not overwritten (changed on disk: another copy of BAYSOL saved it; reopen it). A project deleted in one copy is not brought back by the other. Starting a run takes a lock too, so two copies starting at the same instant cannot both win; a refused start says a run is in progress (pid N), and delete run and delete project refuse a live run.

For contributors

The interface only reads and writes the project's JSON files and starts programs; Julia knows nothing about it. BAYSOL.run_project (Julia) is the one entry the interface calls, with the arguments project_dir, temperature, ui = :tui and run_dir; the same JSON files are read by Julia's load_settings and load_buffer, and the test fixtures test/fixtures/settings/*.json and test/fixtures/buffer/*.json at the repository root are shared by both sides, so a change to a file format changes both.

Layout of tui/src (four folders):

FolderWhat lives there
core/no UI: environment.ts (folders, the cache, asset lookup, the RUN_FLOW and LOGS_FLOW constants, the Julia command), terminal.ts (text width, wrapping, number parsing, hasTerminal), file-system.ts (JSON files, atomic writes, locks)
store/the data layer, no React: settings, projects and the run folder, buffer and solutes, the add flow, custom solutes, data import, the run session and its logs, the viewer's data
ui/the kit every screen is built from: interaction.tsx (the navigation stack, all key definitions, text input, cursor lists), theme.tsx, grid.tsx (menus and legends), input.tsx (prompts, dropdowns, questions, the theme picker), frame.tsx (the screen frame and forms)
screens/the screens: menus, data, solutes, custom solutes, settings, the run screen, the viewer and open runs

main.tsx is start-up only (it needs a terminal, sweeps stale runs, installs the SIGHUP and SIGTERM handlers); app.tsx is the App component (theme, size guard, the Ctrl-C handler, the navigation stack). assets/ has the logos, the menu pictures and the data files (setting_sheets.json is the settings sheets).

Architecture in short. Every key goes through one route: a screen calls useKeys(handler, active) and the handler asks press.is(keys.x); keys are defined once in ui/interaction.tsx (and the menu hotkeys in ui/grid.tsx), never spelled elsewhere, and legends are built from the same definitions, so the hint can only list keys that work. State lives in store/; a screen is a thin view. A run is a Julia child process in its own process group, started by RunSession after the claim of a run folder under a lock; run.json has one writer (Julia) and liveness is status running plus a heartbeat under 60 s; the session aborts the group with SIGTERM and a grace time, then SIGKILL.

Commands (from tui/, or the repository root with -w tui):

npm start       # run it
npx tsc         # type-check (strict, no emit; also `npm run check`)
npm test        # the node:test suite (tsx --test test/*.test.ts); takes minutes

Formatting and lint are the repository's: bysl fmt runs Biome (installed at the root) and the TypeScript whitespace rule, bysl fmt --lines fails on a line over 92 columns or an indentation that is not a multiple of 4 (exactly 4 spaces per level, continuation lines too), and bysl precommit runs everything before a commit. Every source file starts with # SPDX-License-Identifier: LGPL-3.0-or-later in its comment syntax (bysl fmt adds it).

Tests. Pure logic is unit-tested with node:test (test/*.test.ts); the run flow is tested with real processes (concurrency.test.ts: two processes claim a run, exactly one wins; a killed child becomes interrupted) and a stand-in for Julia, test/support/fake-julia.ts (modes done, failed, hang, ...; the environment variable JULIA=<script> makes the whole program use it). Tests never touch your data or cache folders: they use throwaway ones.

Checking a screen by hand. Screens have no render tests; drive the real program in a pseudo-terminal: start npm start with BAYSOL_HOME and BAYSOL_CACHE pointing at scratch folders, a window size of 80 x 24 set with TIOCSWINSZ, wait a few seconds for the start, feed keystrokes, and read the screen with a terminal emulator library (for example Python's pty and pyte). Decode the output as a stream (a multi-byte character can be split between reads). The blocks in this guide were captured that way. Never point such a run at the real data folder.

The earlier Clojure interface is gone; tui/SPEC.md is its specification, kept as the reference of the rules, numbers and messages the TypeScript version preserves.
